WebRTC Peer-to-Peer Streaming in Web Applications

WebRTC (Web Real-Time Communication) enables direct peer-to-peer audio and video streaming between web browsers without requiring third-party plugins or dedicated media streaming servers. This article explores how modern web applications use native browser APIs, signaling channels, and network traversal mechanisms to capture user media, negotiate secure network connections, and stream live audio and video directly inside standard HTML elements.

1. Capturing Local Media

The streaming process begins on the client side using the navigator.mediaDevices.getUserMedia() JavaScript API. This method requests user permission to access camera and microphone hardware. Once granted, the browser creates a MediaStream object containing distinct audio and video tracks, which can be previewed immediately in an HTML <video> or <audio> element by assigning the stream to the element's srcObject property.

2. Signaling and Session Negotiation

Browsers cannot discover each other automatically across the internet. To initiate a connection, they use an external signaling channel—typically implemented with WebSockets, HTTP requests, or server-sent events. WebRTC does not define a specific signaling protocol, leaving developers free to choose how metadata is transferred.

During signaling, peers exchange connection metadata using the Session Description Protocol (SDP).

  • The initiating peer creates an "offer" via RTCPeerConnection.createOffer(), which details supported audio/video codecs, resolutions, and media configurations.
  • The receiving peer sets the incoming offer as its remote description and generates an "answer" via RTCPeerConnection.createAnswer(), specifying which proposed configurations it supports.
  • Once both peers register their local and remote descriptions, they agree on the format of the media to be exchanged.

3. NAT Traversal via ICE, STUN, and TURN

Most consumer devices sit behind routers using Network Address Translation (NAT) and strict firewalls, obscuring their public IP addresses. WebRTC solves this using the Interactive Connectivity Establishment (ICE) framework.

  • STUN (Session Traversal Utilities for NAT): Peers query a STUN server to discover their public IP address and port mapping.
  • ICE Candidates: Each potential connection address discovered (local network IP, public STUN-mapped IP) is packaged as an ICE candidate and transmitted to the other peer via the signaling channel.
  • TURN (Traversal Using Relays around NAT): If restrictive symmetric firewalls block direct connection attempts entirely, traffic falls back to a TURN server, which relays encrypted media packets between the two peers.

4. Securing and Establishing the Channel

Once a viable pair of ICE candidates is selected, the browsers establish a direct network link over UDP. WebRTC enforces end-to-end encryption for all real-time traffic. The connection is secured using Datagram Transport Layer Security (DTLS) to generate cryptographic keys, while the actual audio and video packets are encrypted and transmitted using the Secure Real-time Transport Protocol (SRTP).

5. Media Playback in the Browser

When the secure data path is open, incoming media packets are reconstructed into a remote MediaStream by the receiving browser. The RTCPeerConnection fires a track event, giving JavaScript access to the stream. By assigning this incoming stream to the srcObject of an HTML <video> element, the media plays natively within the webpage with ultra-low latency.
