Preventing DOM XSS with Trusted Types in HTML

Trusted Types is a modern browser security feature designed to eliminate DOM-based Cross-Site Scripting (DOM XSS) vulnerabilities by locking down unsafe injection sinks. This article explains the fundamental purpose of Trusted Types, how they transition web applications from vulnerable raw string assignments to strictly typed objects, and how combining them with Content Security Policy (CSP) guarantees that data is sanitized before it enters the Document Object Model.

The Problem with DOM-Based XSS

DOM-based XSS occurs when client-side JavaScript reads user-controllable input (the source) and passes it directly into an execution-prone browser API (the sink). Common sinks include Element.innerHTML, Element.outerHTML, document.write, and eval().

Historically, securing these sinks relied entirely on developer discipline to remember to sanitize or encode strings before assigning them. In large codebases with multiple developers and complex dependency trees, relying on manual vigilance often fails, leaving sinks exposed to injection attacks.

The Purpose of Trusted Types

The primary purpose of Trusted Types is to restrict dangerous DOM sinks so they no longer accept arbitrary strings. Instead, the browser requires developers to pass specially constructed, type-safe objects: TrustedHTML, TrustedScript, and TrustedScriptURL.

By default, without Trusted Types, writing:

element.innerHTML = userInput;

is accepted directly by the browser, even if userInput contains malicious payload scripts.

With Trusted Types enforced, assigning a plain string to an unsafe sink immediately throws a runtime TypeError. This forces developers to funnel all sink-bound data through a controlled verification pipeline.

How Trusted Types Enforce Safety

Trusted Types function through a policy-based architecture:

  1. Defining Policies: Developers create named policies using the window.trustedTypes.createPolicy() API. A policy defines transformation rules—typically integrating robust sanitization libraries like DOMPurify—that convert unsafe input into a TrustedHTML object.
  2. Assigning Safe Objects: Once processed, the resulting trusted object, rather than a raw string, is assigned to the sink: 
    const sanitizePolicy = trustedTypes.createPolicy('mySanitizer', {
  createHTML: (string) => DOMPurify.sanitize(string)
});

element.innerHTML = sanitizePolicy.createHTML(userInput);
  3. Browser Enforcement: The browser validates the object’s internal type before parsing or executing the code. If an attempt is made to bypass the policy using a plain string, the browser blocks execution.

Policy Enforcement via Content Security Policy (CSP)

To enforce this behavior across an entire web application, developers use the HTTP Content-Security-Policy header:

Content-Security-Policy: require-trusted-types-for 'script';

When this directive is active, the browser enters strict mode. Every injection sink on the page refuses strings globally. Teams can also restrict which policies are allowed to create trusted objects using the trusted-types directive, preventing rogue or third-party scripts from declaring unsafe policies:

Content-Security-Policy: require-trusted-types-for 'script'; trusted-types mySanitizer;

Key Security Benefits

  • Centralized Sanitization Logic: Security teams no longer have to audit thousands of individual DOM assignments across an application. They only need to audit the specific Trusted Types policies defined in the codebase.
  • Proactive Prevention: Vulnerabilities are identified early during development or automated testing, as any unhandled string assignment throws an immediate error.
  • Elimination of Sink Insecurity: By making the browser itself reject dangerous input patterns, an entire class of DOM-based injection attacks is eliminated by design.
