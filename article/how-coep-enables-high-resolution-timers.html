How COEP Enables High-Resolution Timers

The Cross-Origin Embedder Policy (COEP) isolates an HTML document by preventing it from loading any cross-origin resources that have not explicitly granted permission to be embedded. When combined with Cross-Origin Opener Policy (COOP), COEP places the document in a secure, cross-origin isolated execution context. This isolation mitigates the risk of Spectre-style side-channel attacks, allowing web browsers to safely restore powerful browser features, including microsecond-precision high-resolution timers and SharedArrayBuffer.

The Security Problem: Spectre and Timers

In 2018, the discovery of the Spectre vulnerability revealed that speculative execution in modern CPUs could be exploited to read sensitive memory data across security boundaries. Attackers could measure the exact time it takes to access data in the CPU cache to infer private memory contents.

To execute a cache-timing attack, an attacker requires:

  1. Access to sensitive cross-origin data in the same process memory.
  2. An extremely precise clock to measure microsecond or nanosecond timing differences.

To neutralize this threat, browser vendors coarsened the resolution of timers like performance.now() and disabled features like SharedArrayBuffer, which could be repurposed as high-precision timers via web workers.

How COEP Establishes Document Isolation

Browsers introduced the "cross-origin isolated" state to safely re-enable high-performance features. COEP is the resource-loading gatekeeper for this state.

When a server sends the HTTP header:

Cross-Origin-Embedder-Policy: require-corp

The browser refuses to load any cross-origin resource (such as images, scripts, stylesheets, or iframes) unless the resource explicitly opts into being loaded. A third-party resource can opt in by serving one of the following headers:

  • Cross-Origin Resource Policy (CORP): Cross-Origin-Resource-Policy: cross-origin
  • Cross-Origin Resource Sharing (CORS): Providing standard CORS headers such as Access-Control-Allow-Origin: *

Alternatively, the credentialless directive can be used:

Cross-Origin-Embedder-Policy: credentialless

Under credentialless, requests to cross-origin resources without CORP headers are sent without credentials (cookies, client certificates), preventing authenticated sensitive data from entering the process.

The Role of COOP

COEP cannot secure a document alone. It works in conjunction with the Cross-Origin Opener Policy (COOP):

Cross-Origin-Opener-Policy: same-origin

While COEP restricts what a document can load as subresources, COOP ensures that cross-origin windows cannot retain a direct DOM reference to the document, and vice versa. Together, COOP and COEP guarantee that untrusted cross-origin code and data never reside in the same browsing context group or process.

Unlocking High-Resolution Timers

When an HTML document delivers both Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp (or credentialless), the browser designates the environment as cross-origin isolated. This can be verified in JavaScript via:

if (self.crossOriginIsolated) {
  // Document is isolated; high-performance features are available
}

With complete control over what memory enters the process, the risk of side-channel data leakage is virtually eliminated. Consequently, the browser lifts security restrictions:

  • performance.now(): Timing precision is restored from coarsened millisecond increments back to microsecond fidelity (e.g., 5 microseconds or better, depending on the browser engine).
  • SharedArrayBuffer: Web Workers can share memory directly without risk of creating ad-hoc high-precision timers across cross-origin contexts.

By using COEP to strictly control resource embedding, the web platform separates sensitive data from untrusted contexts, making high-precision timing safe once again.
