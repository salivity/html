Using Cache API with HTML for Offline PWAs

Progressive Web Applications (PWAs) achieve reliable offline functionality through the combined architecture of HTML documents, the Cache API, and Service Workers. By acting as a programmatic network proxy, a Service Worker intercepts HTTP requests initiated by or for an HTML document, checks the Cache API for existing resources, and serves stored assets when a network connection is unavailable. Understanding this relationship requires examining how HTML shells are stored, how request interception works, which caching strategies suit HTML content, and how offline fallbacks are handled.

The Core Triad: HTML, Service Workers, and Cache API

To serve an application offline, three components work synchronously:

  1. HTML Documents: The entry point of the application. The document requests initial CSS, JavaScript, media assets, and registers the Service Worker.
  2. Service Worker: A background JavaScript worker that runs independently of the web page. It acts as an intermediary, intercepting all network requests (including the request for the HTML document itself).
  3. Cache API: A storage mechanism that stores pairs of Request and Response objects. Unlike localStorage, the Cache API is fully asynchronous, accessible within Service Workers, and capable of holding entire HTTP responses, including complete HTML files.

Precaching the HTML Shell

During the Service Worker's install event, the Cache API is populated with critical resources needed to bootstrap the application. This process, known as precaching, commonly targets the foundational HTML structure.

const CACHE_NAME = 'app-shell-v1';
const PRECACHE_ASSETS = [
  '/',
  '/index.html',
  '/offline.html',
  '/styles.css',
  '/app.js'
];

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => {
      return cache.addAll(PRECACHE_ASSETS);
    })
  );
});

Using cache.addAll() performs HTTP GET requests for the specified URLs and stores the matching responses inside the designated cache bucket. When the user later revisits the URL offline, the HTML file is already retained on disk.

Intercepting and Serving HTML Requests

Once the Service Worker is active, it intercepts outgoing network requests via the fetch event listener. When a navigation event occurs (such as a user entering a URL or clicking an internal link), the browser issues a Request with mode: 'navigate'.

The Service Worker inspects this request, queries the Cache API using caches.match(), and decides whether to fetch the response from the live network or return the cached version.

self.addEventListener('fetch', (event) => {
  if (event.request.mode === 'navigate') {
    event.respondWith(
      fetch(event.request).catch(() => {
        return caches.match(event.request).then((cachedResponse) => {
          return cachedResponse || caches.match('/offline.html');
        });
      })
    );
  }
});

In this implementation, the browser first attempts to retrieve the latest HTML document over the network. If the device is offline or the connection fails, the catch block catches the network failure and resolves the request with the cached copy of that specific document. If that specific document was never precached, it falls back to a generic /offline.html page.

Caching Strategies for HTML Documents

Because HTML contains references to versioned scripts, styles, and dynamic content, caching it requires different patterns than static assets like images or fonts:

Network First (Network Falling Back to Cache)

This is the recommended strategy for most HTML navigation requests. It prioritizes fresh data to ensure users see updated markup and current asset hashes. If the network request fails, the application serves the cached version of the HTML document from a previous visit.

App Shell Model (Cache First for Shell, Network for Content)

In single-page applications (SPAs), the primary HTML file serves as an empty shell containing UI scaffolding without dynamic data. The shell can be served with a Cache First strategy for instant loading. Once the cached HTML loads, client-side JavaScript issues requests for data via APIs, which can independently implement runtime caching.

Stale-While-Revalidate

The Cache API immediately serves the existing cached HTML document to deliver an instantaneous page load, while a network request runs concurrently in the background. Once the network request returns, the new HTML response replaces the older version in the Cache API for the next session.

Cache Invalidation and Lifecycle Management

To prevent users from being permanently locked into outdated HTML, caches must be pruned during the Service Worker's activate event. When changes to the HTML or build assets are deployed, updating the cache version name (e.g., from app-shell-v1 to app-shell-v2) triggers the new Service Worker lifecycle.

self.addEventListener('activate', (event) => {
  const currentCaches = [CACHE_NAME];
  event.waitUntil(
    caches.keys().then((cacheNames) => {
      return Promise.all(
        cacheNames.map((cacheName) => {
          if (!currentCaches.includes(cacheName)) {
            return caches.delete(cacheName);
          }
        })
      );
    })
  );
});

Deleting stale caches ensures that old HTML files with references to removed scripts or outdated layouts are purged, allowing the newly installed cache to take complete control of subsequent navigations.
