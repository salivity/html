How iframe sandbox allow-scripts Works

The HTML iframe sandbox attribute restricts the capabilities of embedded content to protect the host page from malicious or untrusted code. By default, applying an empty sandbox attribute disables all dynamic capabilities, including script execution. Adding the allow-scripts token selectively lifts one of the most critical restrictions by re-enabling JavaScript execution inside the framed document, while leaving other crucial security boundaries intact.

The Baseline Sandbox Environment

When an iframe includes the sandbox attribute without any tokens (or with unrelated tokens), the browser places the framed document inside a heavily locked-down, unique-origin environment. In this baseline state:

  • JavaScript execution is completely disabled.
  • Form submissions are blocked.
  • Popups, modals, and new tabs cannot be spawned.
  • Storage mechanisms like localStorage and document.cookie are unavailable.
  • Navigation of the parent or top-level browsing context is prevented.

How allow-scripts Modifies Execution

Adding allow-scripts specifically reactivates the embedded document's JavaScript runtime. Once applied, the framed page can:

  • Run inline <script> tags and load external script files.
  • Execute event listeners (such as click, mousemove, and load).
  • Use browser timers and timing APIs like setTimeout, setInterval, and requestAnimationFrame.
  • Make asynchronous network requests using fetch() or XMLHttpRequest, subject to standard Cross-Origin Resource Sharing (CORS) rules.

Persistent Restrictions

Enabling allow-scripts does not grant unrestricted access. Unless additional tokens are explicitly declared, the iframe environment still enforces substantial limitations:

  • Unique Origin (Cross-Origin Isolation): The document continues to run in a unique, opaque origin (null). Even if the framed page is hosted on the same domain as the parent page, scripts cannot access parent DOM nodes, inspect parent variables, or read parent cookies.
  • Storage Access: Because the origin is treated as unique, APIs that rely on persistent origin-based storage (such as localStorage and IndexedDB) remain restricted or inaccessible.
  • No Top Navigation: Scripts cannot redirect the parent page via window.top.location unless the allow-top-navigation token is also supplied.
  • No Unsolicited Popups: Calls to window.open() remain blocked unless paired with allow-popups.

Critical Security Risk: Pairing with allow-same-origin

A well-known vulnerability occurs when combining allow-scripts with allow-same-origin on an untrusted page hosted on the same origin as the parent site. When both tokens are present, the framed script executes within the parent's actual origin rather than an opaque one. This allows the embedded script to access the parent page's DOM and programmatic interfaces directly, enabling it to remove the sandbox attribute entirely and bypass all intended security boundaries.
