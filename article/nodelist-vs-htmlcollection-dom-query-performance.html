NodeList vs HTMLCollection: DOM Query Performance

This article examines the performance differences between static NodeLists and live HTMLCollections when querying and manipulating the Document Object Model (DOM). While live HTMLCollections typically offer faster initial query execution due to their lightweight, reference-based nature, static NodeLists provide superior performance and predictability during iteration and DOM mutation. Understanding the mechanics of how the browser engine resolves each collection type enables developers to select the optimal DOM querying method, avoiding common pitfalls such as layout thrashing, forced synchronous reflows, and unintended infinite loops.

Understanding Live HTMLCollections and Static NodeLists

The primary distinction between an HTMLCollection and a standard NodeList returned by selector queries lies in how they track state:

  • Live HTMLCollection: Generated by methods such as document.getElementsByTagName, document.getElementsByClassName, and properties like element.children. These collections are live views of the DOM. When the underlying DOM tree changes, the collection automatically reflects those changes without re-querying.
  • Static NodeList: Generated primarily by document.querySelectorAll. This collection is a frozen snapshot of the DOM at the exact moment the query was executed. Subsequent additions, deletions, or modifications to the DOM do not alter the contents or size of a static NodeList.

(Note: NodeList can also be live when accessed via properties like Node.childNodes, but queries via selectors always return static instances).

Initial Query Execution Speed

In raw query execution benchmarks, methods returning live HTMLCollections are almost universally faster than querySelectorAll.

Methods like getElementsByClassName or getElementsByTagName perform simple, specialized lookups. Modern browser engines maintain internal indices for tag names and classes, allowing these methods to return an HTMLCollection almost instantaneously. The browser does not build a full array of elements immediately; instead, it returns an object that dynamically references the engine's internal DOM representation.

Conversely, querySelectorAll must parse and evaluate arbitrary CSS selector strings, perform a complete traversal of the matching DOM subtree, and construct a fixed list of matching nodes. This parsing and upfront snapshot generation incurs an initial CPU and memory overhead.

Access and Iteration Costs

While live collections win on initial retrieval, static collections consistently outperform live ones during iteration and read operations.

Because an HTMLCollection is live, accessing properties like .length or retrieving an item by index (collection[i]) may require the browser engine to re-validate the collection against the current state of the DOM tree. If an iteration relies on dynamically checking .length at every step:

// Costly with a live HTMLCollection
const items = document.getElementsByClassName('item');
for (let i = 0; i < items.length; i++) {
  // Accessing items.length can force DOM re-verification
  doSomething(items[i]);
}

In this pattern, each iteration step can cause the browser to re-evaluate the DOM, leading to an \(O(n^2)\) complexity profile in certain engines.

With a static NodeList, the .length property and indices are fixed numbers stored in memory. The iteration cost is equivalent to traversing a standard JavaScript array, running at a predictable \(O(n)\) time complexity.

The Cost of DOM Mutation

The performance disparity widens significantly when queries involve modifying the DOM inside a loop.

Modifying elements inside an HTMLCollection loop forces the engine to recalculate the collection's contents dynamically. If elements matching the query are added or removed during the loop, this causes performance degradation through constant cache invalidation. In severe cases, it alters the indices mid-loop, producing infinite loops or skipped nodes.

A static NodeList isolates the execution loop from the live DOM. Because the snapshot does not update when nodes are added or removed, the browser does not need to invalidate and synchronize the collection during DOM writes.

Memory Footprint

Live collections typically have a smaller initial memory footprint because they act as lightweight dynamic wrappers over the existing DOM structure.

Static NodeLists consume more memory because they allocate storage for references to every matching node at that specific point in time. If a static NodeList containing thousands of nodes remains in scope within a long-running JavaScript process, it prevents garbage collection of those DOM nodes, even if they are subsequently removed from the active document.

Summary of Usage Recommendations

  • Use querySelectorAll (Static NodeList) when you need complex CSS selectors, plan to modify the DOM during iteration, or require an immutable snapshot that guarantees predictable loop performance.
  • Use getElementsByClassName or getElementsByTagName (Live HTMLCollection) for performance-critical initial lookups where you only need to read a small subset of elements, or when you immediately convert the collection into a native array (e.g., Array.from()) to neutralize the live overhead.
  • Always cache the .length property in a local variable if you must loop over a live HTMLCollection to prevent repeated DOM state checks.
