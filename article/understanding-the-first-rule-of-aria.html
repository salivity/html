Understanding the First Rule of ARIA

This article provides an overview of the First Rule of ARIA (Accessible Rich Internet Applications), explaining its core directive regarding native HTML semantics. You will learn why web developers are strongly advised to prioritize built-in HTML elements over custom ARIA attributes, the technical benefits of this approach for accessibility, and the specific scenarios where applying ARIA is truly necessary.

The First Rule of ARIA, defined by the W3C, states: If you can use a native HTML element or attribute with the semantics and behavior you require already built in, instead of repurposing an element and adding an ARIA role, state, or property to make it accessible, then do so.

In short: Use native HTML instead of ARIA whenever possible.

Why Native HTML Takes Precedence

Native HTML elements provide essential accessibility features automatically, requiring no extra JavaScript or ARIA markup to function correctly:

  • Built-in Keyboard Accessibility: Elements like <button>, <select>, and <a> are focusable via the Tab key and respond to keyboard interactions (such as Enter and Space) right out of the box.
  • Semantic Meaning: Assistive technologies, such as screen readers, automatically recognize the role and state of native elements without additional code.
  • Less Maintenance: Using native elements significantly reduces the amount of custom code needed to manage focus, states, and keyboard events.

A Practical Comparison

Consider creating a clickable button.

The Incorrect Approach (Relying on ARIA):

<div role="button" tabindex="0">Click Me</div>

Using a <div> with role="button" tells a screen reader that the element is a button, but it does not actually behave like one. To make this accessible, you must manually write JavaScript to handle keydown events for Enter and Space, manage focus styles, and handle disabled states.

The Correct Approach (The First Rule in Action):

<button type="button">Click Me</button>

The native <button> element provides keyboard focus, activates with keyboard presses, announces its role to assistive software, and supports attributes like disabled automatically.

When Should ARIA Be Used?

The First Rule does not mean ARIA should never be used. ARIA is essential when:

  • HTML lacks a native semantic equivalent for a design pattern (such as tabs, tree views, or modal dialogs).
  • You need to expose dynamic states or properties that native HTML cannot convey, such as aria-expanded="false" or aria-live="polite".
  • Visual design or legacy constraints prevent the use of standard native elements.

ARIA is intended to fill the gaps in HTML, not to replace native elements. When building accessible interfaces, the most reliable practice is to start with semantic HTML and only layer in ARIA when native capabilities fall short.
