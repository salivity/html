requestAnimationFrame: Syncing DOM Updates with Screen

The requestAnimationFrame() API is a native browser method designed to synchronize JavaScript-driven DOM updates with the display hardware's native refresh cycle. Instead of relying on unpredictable timers, it instructs the browser to execute a specified callback right before the next repaint occurs. This overview explains how requestAnimationFrame() eliminates visual stutter, adapts dynamically to varying monitor refresh rates, optimizes system resources, and batches layout changes for fluid user interfaces.

The Problem with Traditional Timers

Before requestAnimationFrame(), developers used setTimeout() and setInterval() to create animations. These methods are fundamentally detached from the display hardware.

A standard display updates at a fixed interval governed by a vertical synchronization (VSYNC) signal—typically every 16.67 milliseconds on a standard 60Hz display. Timers run on the JavaScript event loop queue and are prone to delays caused by other executing tasks. If a timer fires midway through a refresh cycle, the browser cannot render the update until the next cycle, resulting in dropped frames (jank) or visual tearing, where parts of two different frames appear on the screen simultaneously.

The Role of requestAnimationFrame()

requestAnimationFrame() resolves timing mismatches by transferring scheduling control from the script to the browser's rendering engine. When invoked, it schedules a callback function to run during the browser's render pipeline, immediately before the style calculation, layout, and paint stages take place.

Key operational roles include:

  • VSYNC Synchronization: The browser aligns JavaScript execution directly with the display's VSYNC signal. This guarantees that DOM mutations are captured and painted in the very next frame, preventing frame skipping.
  • Dynamic Refresh Rate Adaptation: Different displays operate at different frequencies, such as 60Hz, 120Hz, or 144Hz. requestAnimationFrame() automatically matches the target display's refresh rate without requiring hardcoded intervals. On a 120Hz screen, it fires roughly every 8.33 milliseconds; on a 60Hz screen, it fires every 16.67 milliseconds.
  • Layout and Paint Batching: Because callbacks run just prior to the browser's restyle and layout calculations, all DOM updates made across multiple animations can be computed and painted in a single pass, drastically reducing layout thrashing.
  • Resource Conservation and Throttling: When a browser tab is minimized, placed in the background, or hidden behind another window, the browser automatically pauses or dramatically slows down requestAnimationFrame() execution. This minimizes CPU and GPU usage and preserves battery life on mobile devices, an optimization that standard timers do not natively provide.

Standard Implementation Pattern

To build a continuous animation, requestAnimationFrame() is called recursively inside its own callback function. The browser passes a high-resolution timestamp (DOMHighResTimeStamp) to the callback, representing the exact time the frame started rendering.

let startTimestamp = null;
const element = document.getElementById('animatedElement');

function step(timestamp) {
  if (!startTimestamp) startTimestamp = timestamp;
  const progress = timestamp - startTimestamp;

  // Update DOM properties based on elapsed time
  element.style.transform = `translateX(${Math.min(progress / 10, 200)}px)`;

  // Continue the loop if the condition is met
  if (progress < 2000) {
    window.requestAnimationFrame(step);
  }
}

// Initiate the animation
window.requestAnimationFrame(step);

Using the provided timestamp allows animations to be time-based rather than frame-based, ensuring that movement remains consistent regardless of whether the user is on a high-refresh monitor or experiencing temporary frame rate drops. By aligning code execution directly with the display cycle, requestAnimationFrame() serves as the foundational mechanism for high-performance rendering on the modern web.
