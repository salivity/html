How LCP Measures Render Speed of Images and Text

Largest Contentful Paint (LCP) is a Core Web Vital metric that measures perceived page load speed by tracking when the largest visual content element becomes fully rendered within the user's viewport. This article breaks down how the browser identifies qualifying image and text blocks, calculates their dimensions, and records their precise render timestamps during the page-loading lifecycle.

Qualifying Elements for LCP

The browser's PerformanceObserver API monitors specific types of DOM elements to determine LCP candidates. Only primary content elements that represent substantial visual weight are considered:

  • Image Elements: Standard <img> tags and <image> elements embedded inside an SVG.
  • Video Elements: The poster image or the first displayed frame of a <video> element.
  • Background Images: Elements styled with a CSS background-image loaded via the url() function.
  • Text Blocks: Block-level HTML elements (such as <h1> through <h6>, <p>, <ul>, or structural wrappers like <div> and <section>) containing text nodes or inline text children.

How Element Size is Calculated

To identify which element is the "largest," the browser measures the visible surface area of qualifying candidates within the initial viewport:

  • Viewport Boundaries: Only the portion of the element visible on the screen is measured. Any content extending outside the viewport, hidden via CSS (display: none, visibility: hidden, or opacity set to 0), or clipped by overflow is excluded.
  • Images: The measured size is the smaller of the element’s intrinsic (natural) size or its rendered layout size. This prevents developers from manipulating LCP scores by scaling up small, low-resolution images to fill the screen.
  • Text Blocks: The browser calculates the smallest bounding box enclosing all rendered text nodes within the block. Margins, paddings, and borders outside the text itself are ignored.

The Render Timing Process

LCP measurement is dynamic and updates progressively as the browser builds the Document Object Model (DOM) and paints pixels to the screen:

  1. Candidate Tracking: As the HTML parses and assets download, the browser renders elements sequentially. Each time an element renders that is larger than any previously painted element, the browser records a new performance entry.
  2. Element Mutation: If an existing element changes size or is removed from the DOM, the browser adjusts its calculations accordingly.
  3. Finalization: The browser stops tracking new LCP candidates the moment the user interacts with the page (via tapping, clicking, or scrolling), as user actions alter page layout and perceived performance. The timestamp of the last recorded largest candidate marks the official LCP score.

Breakdown of the LCP Timing Window

The total LCP duration comprises four distinct phases:

  • Time to First Byte (TTFB): The time from the user's navigation request until the browser receives the first byte of the HTML document.
  • Resource Load Delay: The gap between receiving the HTML and the browser discovering and initiating the request for the LCP resource (critical for external images or web fonts).
  • Resource Load Duration: The time spent downloading the LCP asset over the network.
  • Element Render Delay: The remaining time required to decode the asset, apply styles, resolve layout calculations, and paint the pixels to the screen.

An optimal LCP measurement occurs within 2.5 seconds or less of the initial navigation, ensuring that users see the core content of a webpage almost immediately upon arrival.
