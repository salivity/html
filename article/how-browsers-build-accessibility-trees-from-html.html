How Browsers Build Accessibility Trees from HTML

The accessibility tree is a specialized representation of a web page constructed by the browser engine to enable assistive technologies, such as screen readers, to interact with web content. While the browser parses raw HTML into the Document Object Model (DOM) and computes styles via the CSS Object Model (CSSOM), it simultaneously translates these nodes into an internal hierarchy of accessible objects. This article explains the technical pipeline browsers use to derive accessible roles, states, and properties from HTML semantics, apply CSS modifications, and expose the final structure to operating system accessibility APIs.

1. HTML Parsing and DOM Construction

The process begins with the browser’s HTML parser. As raw bytes are streamed over the network, the browser tokenizes the markup and constructs the standard DOM tree. Each element in the markup is instantiated as a DOM node. At this initial phase, elements carry implicit semantic contracts defined by the HTML specification—for example, <button> denotes an interactive trigger, and <input type="checkbox"> denotes a binary toggleable input.

2. Semantic Mapping via HTML-AAM

Browsers do not invent accessibility rules on the fly; they adhere to the HTML Accessibility API Mappings (HTML-AAM) specification. As DOM nodes are created, the engine matches native HTML elements to corresponding accessibility characteristics:

  • Role: Identifies what an element is (e.g., button, heading, checkbox, navigation).
  • Name: The accessible label of the element (derived from text content, alt attributes, associated <label> elements, or aria-label).
  • State: The current condition of the element (e.g., checked, disabled, expanded).
  • Value: The current value, if applicable (e.g., the text inside an input field or a progress bar's range).

For example, when a <nav> tag is encountered, the browser automatically maps it to a landmark role of navigation without requiring explicit author configuration.

3. Applying ARIA Attributes

Once native semantics are determined, the browser evaluates any Accessible Rich Internet Applications (WAI-ARIA) attributes present on the elements. ARIA attributes allow developers to alter or enhance implicit semantics:

  • Role Overrides: An explicit role="..." overrides the element’s native semantic role (e.g., <div role="button">).
  • State and Property Augmentation: Attributes such as aria-expanded="true" or aria-haspopup="menu" inject additional state data into the accessible node.

ARIA cannot alter native element behavior or focusability in the DOM; it strictly modifies the data passed to the accessibility tree.

4. Style Computation and Pruning

The accessibility tree is not a direct 1:1 mirror of the DOM tree. It represents only what is perceptually and functionally relevant to assistive technology users. The browser integrates computed styles from the CSSOM to determine node visibility and inclusion:

  • Removal via Display and Visibility: Elements styled with display: none or visibility: hidden are removed entirely from the accessibility tree, as are elements with the hidden or aria-hidden="true" attributes.
  • Pseudo-elements: Generated content such as ::before and ::after containing text via the content property is integrated into the accessibility tree so screen readers can announce it.
  • Structural Flattening: Purely presentational elements without semantics, text, or interactive behavior (such as non-semantic <div> or <span> elements used solely for layout) are frequently pruned from the accessibility tree to optimize performance and navigation.

5. Accessible Name and Description Computation

For every node included in the tree, the browser runs the Accessible Name and Description Computation (AccName) algorithm. The browser searches for identifying text in a strict order of precedence:

  1. aria-labelledby references.
  2. Direct aria-label attributes.
  3. Native labeling mechanisms (such as <label for="...">, the alt attribute on an <img>, or caption on a <table>).
  4. Subtree text content (such as the text between <button> and </button>).
  5. Fallback attributes, such as title or placeholder.

6. Translation to Operating System APIs

Browsers do not communicate directly with screen readers. Instead, the browser engine translates its internal accessibility tree into the platform-specific accessibility APIs provided by the underlying operating system:

  • Windows: UI Automation (UIA) and IAccessible2.
  • macOS and iOS: NSAccessibility and UIAccessibility.
  • Linux: AT-SPI (Assistive Technology Service Provider Interface).
  • Android: Android Accessibility Framework.

Each operating system API expects specific interfaces, data structures, and events. The browser functions as an intermediary, updating the platform-native objects whenever the DOM or CSSOM mutations occur.

7. Reactive Updates to Tree Mutations

The accessibility tree is dynamic. When JavaScript modifies the DOM (such as appending a child node, changing an attribute, or altering CSS classes), the browser fires internal mutation events. The engine recalculates the affected nodes, updates their roles, states, or names, and emits corresponding platform-level accessibility events (such as an alert event or a focus change event) to notify assistive technologies in real time.
