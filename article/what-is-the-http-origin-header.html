What Is the HTTP Origin Header?

The HTTP Origin request header indicates the source origin—composed of the protocol, domain name, and port—from which a web request originates. This article explains how browsers automatically use the Origin header during fetch calls and HTML form submissions, how it differs from similar headers like Referer, and why servers rely on it to enforce Cross-Origin Resource Sharing (CORS) and defend against Cross-Site Request Forgery (CSRF) attacks.

Anatomy of an Origin

An origin is defined by three components:

  • Scheme: The protocol (e.g., https://)
  • Hostname: The domain or IP address (e.g., example.com)
  • Port: The communication endpoint (e.g., :443, often omitted if default)

Unlike a full URL, an origin contains no path, query parameters, or fragment identifiers. For example, a request originating from https://sub.example.com:8080/dashboard?user=1 produces the origin value:

Origin: https://sub.example.com:8080

The Function of the Origin Header in fetch Requests

When a script uses the fetch() API or XMLHttpRequest to request data from another domain, the browser implements Cross-Origin Resource Sharing (CORS) mechanics:

  1. Automatic Inclusion: For cross-origin requests, the browser automatically attaches the Origin header. JavaScript cannot modify, override, or delete this header, making it trustworthy for the receiving server.
  2. Preflight Checks: For non-simple requests (such as requests sending application/json or custom headers), the browser sends an OPTIONS preflight request with the Origin header to ask the server for permission.
  3. Access Control: The target server inspects the Origin header. If the origin is permitted, the server responds with Access-Control-Allow-Origin: <origin>. If the origin is rejected or omitted, the browser blocks the JavaScript client from accessing the response.

In same-origin fetch requests, modern browsers omit the Origin header for GET and HEAD methods, but usually include it for state-modifying requests like POST, PUT, and DELETE.

The Function of the Origin Header in HTML Forms

Standard HTML form submissions (<form method="POST">) traditionally navigate the user directly to the action URL rather than processing responses through client-side scripts. Historically, forms relied on the Referer header to indicate where the user came from.

Modern browsers send the Origin header on cross-origin form submissions (specifically POST methods) to improve security:

  • CSRF Defense: If a malicious website attempts to submit a hidden form to your banking application, the user's browser sends the malicious site's domain in the Origin header (e.g., Origin: https://malicious-site.com). The target application checks this header and rejects the submission if it does not match its trusted origins.
  • Form GET vs. POST: Form submissions using method="GET" do not typically send an Origin header because GET requests are intended to be idempotent and safe, representing resource retrieval rather than state changes.

Origin vs. Referer

While both headers communicate where a request started, they serve distinct purposes:

  • Privacy: The Referer header contains the full URL, including path segments and query strings, which may inadvertently expose sensitive information. The Origin header strictly contains the scheme, host, and port, preserving user privacy.
  • Reliability: Browsers frequently strip or redact the Referer header based on the site's Referrer-Policy (such as downgrading from HTTPS to HTTP). In contrast, browsers enforce the Origin header specifically for cross-origin security handshakes.
  • Presence: Referer is typically sent on standard link navigations; Origin is targeted toward CORS requests, preflights, and state-changing HTTP requests.

How Servers Should Use the Origin Header

  1. Validate against an allowlist: Compare the Origin value against an explicit list of trusted domains. Avoid dynamically reflecting the incoming Origin value into Access-Control-Allow-Origin unless the resource is intended to be completely public.
  2. Mitigate CSRF: Verify that the Origin matches your application's domain for incoming state-modifying requests (POST, PUT, DELETE). If the header is present and does not match your domain, reject the request with an HTTP 403 Forbidden status.
  3. Handle null values: The Origin header may be set to null in specific contexts, such as requests from file:// URLs, sandboxed <iframe> elements, or cross-origin redirects. Treat null origins as untrusted.
