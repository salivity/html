How Script Type Module Changes Execution Behavior

Setting the type="module" attribute on an HTML <script> tag informs the browser to treat the code as an ECMAScript Module (ESM) rather than a classic script. This simple declaration fundamentally changes how JavaScript is fetched, parsed, scoped, and executed in the browser environment. Adding this attribute introduces several critical execution behaviors, including automatic deferred execution, strict mode enforcement, lexical module scoping, strict CORS handling, and native support for module loading syntax.

Automatic Deferred Execution

By default, standard classic scripts block HTML parsing: the browser halts rendering to download and execute the script immediately. Adding type="module" automatically gives the script deferred behavior, similar to the defer attribute on classic scripts. The browser downloads module scripts in parallel with HTML parsing and executes them only after the DOM is fully constructed, but right before the DOMContentLoaded event fires. If needed, you can override this behavior by adding the async attribute, which causes the module to execute immediately after it finishes loading.

Enforced Strict Mode

Any code inside a module script automatically executes in JavaScript's strict mode ("use strict"). You do not need to explicitly declare "use strict" at the top of the file. Features that fail silently in sloppy mode will throw runtime errors, undeclared variable assignments are blocked, and certain legacy keywords or behaviors are forbidden.

Scoping and the Global Namespace

In classic scripts, variables declared with var, functions declared at the top level, and declarations generally pollute the global scope (window). With type="module", scripts have their own top-level module scope:

  • Variables, functions, and classes defined at the top level remain private to the module unless explicitly shared using export.
  • Top-level variables do not attach to the window object.
  • The top-level value of this evaluates to undefined, whereas in classic scripts, it refers to window.

Import and Export Capabilities

A script marked as a module unlocks native support for ES module syntax. You can use top-level import and export statements to import other modules, utilities, and components statically, or use dynamic import() for lazy-loading resources. Classic scripts throw a syntax error if static import or export keywords are encountered outside of a module context.

Singleton Execution

A module script executes only once, even if it is referenced multiple times on the same page through separate <script> tags or multiple import declarations across different files. The browser caches the evaluated module and reuses the exported bindings for subsequent requests, preventing duplicate runtime executions and side effects.

Cross-Origin Resource Sharing (CORS)

Module scripts are fetched using CORS rules by default. Unlike classic scripts, which can freely load cross-origin assets without strict CORS validation, module scripts require valid CORS headers (Access-Control-Allow-Origin) if fetched from an external origin. Additionally, module scripts will not execute when loaded via the local file:// protocol in most browsers; they require an HTTP or HTTPS server environment to run.
