How HTML Form Validation Triggers CSS :valid and :invalid

HTML form validation relies on built-in browser constraints to dynamically evaluate user input and apply the :valid and :invalid CSS pseudo-classes. This article explains the underlying mechanics of how native HTML validation attributes connect to the browser's Constraint Validation API, how input states are calculated in real time, and how these evaluations immediately dictate which CSS pseudo-class matches an element.

The Constraint Validation Engine

Modern browsers feature a native Constraint Validation engine that automatically tracks form elements such as <input>, <select>, and <textarea>. Validation is defined directly within HTML using specific constraint attributes, including:

  • required: Mandates that the field must contain a value.
  • type: Enforces specific formats (e.g., type="email", type="url", or type="number").
  • pattern: Matches input against a regular expression.
  • min and max: Constrains numerical or date ranges.
  • minlength and maxlength: Restricts character count.

When an element has one or more of these attributes, the browser monitors changes to the element's value against these criteria.

The ValidityState Object

Beneath the surface, every submittable form control has an associated ValidityState JavaScript object accessed through element.validity. This object contains a set of boolean flags that monitor specific validation rules:

  • valueMissing: True if a required field is empty.
  • typeMismatch: True if the value does not conform to the expected format (e.g., an invalid email).
  • patternMismatch: True if the input fails to match a defined pattern.
  • rangeUnderflow / rangeOverflow: True if the value breaches min or max.
  • tooShort / tooLong: True if length constraints are violated.
  • badInput: True if the browser cannot interpret the entered data.
  • customError: True if a custom message has been set using element.setCustomValidity().

The engine continuously evaluates these flags. If every constraint flag is false, the summary property validity.valid is set to true. If even a single flag evaluates to true, validity.valid is set to false.

How :valid and :invalid Are Triggered

The CSS pseudo-classes :valid and :invalid map directly to the boolean status of element.validity.valid.

  1. Applying :valid: When a form control meets all constraint conditions, validity.valid is true. The browser attaches the :valid pseudo-class to the element, allowing styles like green borders or checkmark icons to render.
  2. Applying :invalid: If any constraint fails, validity.valid becomes false. The browser strips :valid and activates the :invalid pseudo-class, applying error styling such as red borders or alert indicators.

This matching is instantaneous. As the user types, selects, or deletes content, the browser updates the ValidityState object on every input event, which immediately toggles the corresponding pseudo-class in the rendering engine.

Form-Level Matching

The trigger mechanism is not limited to individual controls. Parent <form> elements and <fieldset> containers also react to validation constraints. A <form> will match the :valid selector only if every submittable control within it is valid. If a single descendant control violates a constraint, the parent <form> matches :invalid, allowing developers to style entire forms or submit buttons conditionally based on total form readiness.

Default States and Edge Cases

Understanding the default behavior of constraint validation prevents common styling issues:

  • Empty Optional Fields: An empty, non-required field inherently satisfies all constraints. As a result, it evaluates to validity.valid = true and matches :valid by default.
  • Initial Page Load: Because browsers evaluate constraints immediately upon rendering the DOM, an empty field with a required attribute triggers :invalid instantly, even before a user has interacted with the form. To prevent forms from displaying red error styles on load, developers often pair :valid and :invalid with :not(:placeholder-shown) or rely on the newer :user-invalid and :user-valid pseudo-classes, which only trigger after direct user interaction.
