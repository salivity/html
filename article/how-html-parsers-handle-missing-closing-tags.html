How HTML Parsers Handle Missing Closing Tags

In modern web development, browsers parse HTML using a forgiving, highly standardized algorithm defined by the HTML5 specification. When encountering omitted closing tags like </p> or </li>, the parser does not throw a syntax error; instead, it uses contextual state machine rules to automatically insert implied end tags into the Document Object Model (DOM) tree. This article explains the exact mechanisms the HTML parsing algorithm uses to resolve these missing tags cleanly and deterministically.

Tag Omission vs. Syntax Errors

In HTML, certain closing tags are explicitly designated as optional by the specification, rather than treated as malformed markup. The HTML parsing specification includes a dedicated set of rules called "tag omission" rules:

  • A </p> tag can be omitted if the <p> element is immediately followed by specific block-level elements (such as <div>, <article>, <h1>-<h6>, or another <p>), or if there is no more content in its parent element.
  • An </li> tag can be omitted if the <li> element is immediately followed by another <li> element or if there is no more content in the parent <ul> or <ol>.

Because these rules are formalized, browser engines (such as Blink, Gecko, and WebKit) treat missing optional tags as valid, standard behavior rather than an error recovery scenario.

The Tree Construction Stage and the Stack of Open Elements

The HTML parser operates in two primary phases: tokenization and tree construction.

  1. Tokenization: Breaks the raw HTML string into tokens (start tags, end tags, character data, comments).
  2. Tree Construction: Consumes these tokens and updates the DOM tree while maintaining an internal structure known as the Stack of Open Elements.

The stack of open elements tracks which nodes are currently active. When an element starts, it is pushed onto the stack. When an element ends, it is popped off. The handling of missing tags occurs dynamically during this phase based on the parser’s current "insertion mode."

How the Parser Closes <p> Tags

When the parser is in the "in body" insertion mode and encounters a <p> start tag, it checks if a paragraph element is already open in button scope. If so, it automatically generates an implied end tag for <p>, popping the existing paragraph off the stack before pushing the new one.

Similarly, if the parser encounters a start tag for a block-level element—such as <div>, <ul>, <blockquote>, or <table>—while a <p> tag is on the stack, the following steps occur:

  1. The parser invokes the rule to close a <p> element.
  2. An implied </p> is generated.
  3. The paragraph element is popped from the stack.
  4. The new block-level element is then created as a sibling to the previous <p>, rather than a child.

How the Parser Closes </li> Tags

List items rely on a similar mechanism specifically scoped to list containers:

  1. When the parser encounters an <li> start tag, it inspects the stack of open elements from top to bottom.
  2. It looks for an existing <li> element within the current list scope (stopping if it hits an element other than formatting elements or another <li>).
  3. If an existing <li> is found, the parser emits implied end tags for that element and any unclosed phrasing elements inside it.
  4. The previous <li> is popped from the stack.
  5. The new <li> is initialized and appended to the current parent (<ul> or <ol>).

If the parser encounters the closing tag of the parent list (</ul> or </ol>), it pops all remaining open elements within that list—including any trailing unclosed <li>—until the list container itself is closed.

Result in the DOM

Even though the source markup is missing closing tags, the resulting DOM created by the browser is strictly hierarchical and fully formed. Developers inspecting the rendered page through browser developer tools will observe properly closed nodes that reflect the exact boundary rules governed by the HTML tree construction algorithm.
