How require-trusted-types-for 'script' Stops DOM XSS

The Content Security Policy (CSP) directive require-trusted-types-for 'script' protects HTML documents by locking down client-side injection vectors to prevent Document Object Model-based Cross-Site Scripting (DOM XSS). When enabled, the browser restricts sensitive DOM APIs—known as "injection sinks"—so they no longer accept plain text strings. Instead, these APIs strictly require programmatic, pre-sanitized objects called Trusted Types, ensuring that arbitrary user-controlled data cannot be inadvertently executed as code.

The Problem: Vulnerable DOM Sinks

DOM XSS occurs when an application accepts untrusted data and writes it directly to APIs that parse or execute input. Examples of these sinks include:

  • HTML sinks: Element.innerHTML, Element.outerHTML, and document.write()
  • Script execution sinks: eval(), Function(), and string inputs to setTimeout() or setInterval()
  • Navigation and resource sinks: HTMLScriptElement.src and HTMLIFrameElement.srcdoc

In standard web applications, developers frequently pass unsanitized strings directly to these sinks (e.g., element.innerHTML = location.search). If an attacker manipulates the input, the browser parses the payload as executable markup or script, executing malicious code in the context of the user session.

How the Directive Modifies Browser Behavior

Specifying Content-Security-Policy: require-trusted-types-for 'script' enforces a fundamental behavioral shift at the browser engine level.

Once active, the browser rejects any string assignment to dangerous sinks. If an application attempts to pass a standard string to a sink like innerHTML or script.src, the operation immediately halts, and the browser throws a TypeError. The injection sink refuses to process the data unless it is an instance of a designated Trusted Type:

  • TrustedHTML for sinks that insert markup into the document.
  • TrustedScript for sinks that execute raw JavaScript.
  • TrustedScriptURL for sinks that load external executable scripts.

Creating and Enforcing Policies

To pass data to these sinks, developers must define Trusted Type policies using the JavaScript window.trustedTypes API. A policy dictates the exact sanitization or validation logic applied to incoming data:

// Define a policy to sanitize inputs
const sanitizePolicy = trustedTypes.createPolicy('mySanitizePolicy', {
  createHTML: (input) => {
    // Sanitization logic, such as using DOMPurify
    return DOMPurify.sanitize(input, { RETURN_TRUSTED_TYPE: false });
  }
});

// Using a plain string throws a TypeError:
// element.innerHTML = userInput; 

// Using the policy produces a TrustedHTML object, which succeeds:
element.innerHTML = sanitizePolicy.createHTML(userInput);

Because the policy returns a TrustedHTML object rather than a string, the browser accepts the assignment and safely renders the content.

Centralized Security and Auditability

Without Trusted Types, security teams must audit every single instance where an application modifies the DOM to ensure sanitization occurred. In large codebases with dozens of third-party libraries, ensuring consistent manual sanitization is practically impossible.

The require-trusted-types-for 'script' directive shifts security from distributed, manual code reviews to an automated, centralized model:

  1. Enforced Sanitization: Vulnerable code cannot reach production unchecked; raw string assignments simply fail at runtime.
  2. Narrow Audit Scope: Security reviews shrink from inspecting thousands of sink assignments to reviewing only the declared policy functions where createPolicy is called.
  3. Policy Control: Sites can pair this directive with the trusted-types directive (e.g., trusted-types mySanitizePolicy) to whitelist approved policy names and forbid external scripts from creating their own bypass policies.
