How crossorigin="use-credentials" Handles Cookies

This article explains how the crossorigin="use-credentials" attribute manages authentication cookies when requesting external HTML and web assets. It covers the mechanics of setting the credential mode, the mandatory server-side CORS headers required to allow cookies across origins, browser security restrictions like SameSite policies, and what happens when validation fails.

Default Cross-Origin Behavior

When a browser requests resources such as scripts, stylesheets, or media from a third-party domain, it defaults to an anonymous request mode (crossorigin="anonymous" or omitted). In this default state, the browser strips sensitive credentials—such as HTTP cookies, HTTP authentication headers, and client-side SSL certificates—from the outgoing HTTP request. This prevents the unauthorized sharing of user sessions across different origins.

Enabling Credentials with crossorigin="use-credentials"

Applying crossorigin="use-credentials" to an HTML element (such as <script>, <link>, or <img>) changes the request’s credential mode from same-origin or omit to include.

When this attribute is set:

  1. The browser checks its cookie jar for any cookies matching the target domain specified in the resource's URL.
  2. If matching cookies exist, the browser attaches them to the outgoing request via the standard Cookie header.
  3. The request includes the Origin header indicating the domain of the page requesting the asset.

Server-Side CORS Requirements

Because transmitting authentication cookies across origins introduces security risks such as Cross-Site Request Forgery (CSRF), the browser enforces strict Cross-Origin Resource Sharing (CORS) rules before exposing the response.

For the exchange to succeed, the external server hosting the asset must respond with two specific HTTP headers:

  • Access-Control-Allow-Credentials: true: This explicitly signals to the browser that the server permits credentials in cross-origin interactions.
  • Access-Control-Allow-Origin: <exact-origin>: The server must specify the exact origin of the requesting page (for example, https://example.com). The wildcard value (*) is invalid when credentials are used; if the server responds with *, the browser rejects the response.

Cookie Attribute Constraints

Even if the crossorigin attribute and server CORS headers are properly configured, individual cookie flags can prevent the browser from sending authentication cookies:

  • SameSite Policy: Cookies configured with SameSite=Strict will not be attached to cross-site requests under any circumstances. Cookies with SameSite=Lax are generally omitted from cross-origin subresource requests. To be sent across different origins, the cookie must explicitly be configured with SameSite=None; Secure.
  • Secure Flag: Modern browsers require that any cookie marked SameSite=None must also have the Secure attribute, meaning the request must occur over HTTPS.

Failure Handling

If the target server fails to return Access-Control-Allow-Credentials: true, specifies a wildcard origin, or does not support CORS, the browser blocks the response. The external asset will not be executed or rendered on the page, and the browser's developer console will report a CORS policy violation error.
