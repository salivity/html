Cross-Origin Opener Policy COOP Explained

Cross-Origin Opener Policy (COOP) is a security-focused HTTP response header that allows developers to isolate their web pages from external, cross-origin documents. By restricting how other windows can interact with your document through the DOM, COOP prevents malicious sites from exploiting shared browsing contexts. This article covers the fundamental purpose of COOP, how it severs dangerous execution links between windows, the header values available, and its role in enabling high-performance, secure web APIs.

The Purpose of Browsing Context Isolation

When a web page opens another window via a link (with target="_blank") or JavaScript's window.open(), the browser links both pages within the same browsing context group by default. This relationship provides the opened document with access to window.opener and allows the opener to retain a reference to the opened window.

While legitimate applications use this link for authentication popups or coordinated workflows, it introduces significant security risks:

  • Cross-Site Leaks (XS-Leaks): An attacker's site can manipulate window references to probe history lengths, navigation states, or redirect behaviors to infer sensitive user data.
  • Side-Channel Attacks: Vulnerabilities like Spectre allow attackers to read memory across origins if documents share an operating system process.
  • Window Hijacking: A opened page can alter the opener's location (window.opener.location = 'phishing.html'), misleading the user.

COOP eliminates these vectors by forcing the browser to place the document into a separate top-level browsing context group, effectively setting window.opener to null and isolating the document's execution environment.

COOP Header Directives

You configure COOP by serving the Cross-Origin-Opener-Policy HTTP header from your web server. It accepts three primary directives:

  1. same-origin
    The most restrictive and secure setting. It isolates the document exclusively to other documents from the exact same origin. Any cross-origin window opened by this document, or any cross-origin window that opens this document, will have its window.opener reference severed.

  2. same-origin-allow-popups
    This policy keeps the opener reference if the document opens a popup window, even if that popup does not set COOP. However, it still protects the document from being referenced if it is opened by another site. This is often used for single sign-on (SSO) and OAuth workflows where an application needs to communicate with an identity provider popup.

  3. unsafe-none
    The default browser behavior. The document can be placed in the same browsing context group as its opener, retaining window.opener references unless explicitly overridden by the opener.

Unlocking Modern Web APIs

Beyond direct defense against XS-Leaks and process-level eavesdropping, COOP is a mandatory prerequisite for "cross-origin isolation." Modern high-precision browser features—such as SharedArrayBuffer, high-resolution timers, and advanced performance measurement APIs—were restricted or disabled globally due to their potential use in hardware-based side-channel attacks like Spectre.

To safely re-enable these features, browsers require the page to prove it cannot be manipulated by cross-origin attackers. Delivering both Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp (COEP) places the page in a fully isolated sandbox, allowing safe access to multi-threaded JavaScript and specialized memory APIs.
