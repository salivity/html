Fix Canvas Tainting With the Crossorigin Attribute

When external images are loaded into an HTML5 <canvas> element from a different domain, the browser marks the canvas as "tainted" to uphold the Same-Origin Policy, blocking pixel data extraction. The crossorigin attribute prevents canvas tainting by prompting the browser to make a Cross-Origin Resource Sharing (CORS) request instead of a standard media request. If the host server authorizes the request with the appropriate HTTP headers, the canvas remains clean, allowing developers to read and manipulate pixel data via methods like getImageData(), toDataURL(), and toBlob().

What Is Canvas Tainting?

Canvas tainting is a fundamental browser security mechanism. When an image, SVG, or video originates from a different protocol, domain, or port than the web page hosting the canvas, it is considered cross-origin.

By default, browsers allow cross-origin media to be displayed visually within a canvas using the drawImage() method. However, because pixel data could potentially reveal private user data or protected intranet assets, the browser flags the canvas as tainted. Once a canvas is tainted, the browser prohibits any script from reading back the pixel data, throwing a SecurityError whenever functions such as ctx.getImageData(), canvas.toDataURL(), or canvas.toBlob() are called.

How the crossorigin Attribute Works

The crossorigin attribute changes how the browser requests the asset over the network. By default, media elements (like <img> and <video>) fetch assets without CORS validation. Adding the crossorigin attribute forces the browser to send an Origin HTTP request header containing the current site's domain.

The attribute accepts two values:

  • anonymous: Sends a cross-origin request without user credentials (such as cookies, HTTP authentication, or client-side SSL certificates). This is the standard setting for public assets. Writing crossorigin without a value defaults to anonymous.
  • use-credentials: Sends a cross-origin request that includes credentials like session cookies.

When the browser requests the media using this attribute, it negotiates access with the remote server.

The Role of the Server

The crossorigin attribute alone cannot prevent tainting; it requires explicit consent from the serving domain. The hosting server must respond with the Access-Control-Allow-Origin HTTP header:

  • Access-Control-Allow-Origin: * (allows any domain to read the data)
  • Access-Control-Allow-Origin: https://example.com (allows only the specified origin)

If the server omits this header, or if the origin does not match, the browser blocks the asset entirely, causing an image load error rather than loading a tainted image. When the server returns a valid CORS header matching the origin, the browser recognizes the resource as explicitly shared, marks the data as safe, and leaves the canvas untainted.

Implementation Examples

HTML Implementation

To load an image directly in HTML and process it later in JavaScript, declare the crossorigin attribute on the element:

<img id="source-image" src="https://cdn.example.com/photo.jpg" crossorigin="anonymous">

JavaScript Implementation

When dynamically creating an image object in JavaScript, the crossOrigin property must be set before defining the src attribute to ensure the initial network request carries the CORS headers:

const canvas = document.createElement('canvas');
const ctx = canvas.getContext('2d');

const img = new Image();
img.crossOrigin = 'anonymous'; // Must be set before the src
img.src = 'https://cdn.example.com/photo.jpg';

img.onload = () => {
    canvas.width = img.width;
    canvas.height = img.height;
    ctx.drawImage(img, 0, 0);

    // This operation succeeds without throwing a SecurityError
    const imageData = ctx.getImageData(0, 0, canvas.width, canvas.height);
};

By ensuring that the client requests CORS credentials and the server approves the origin, the crossorigin attribute allows seamless pixel manipulation and data extraction on cross-origin visual media.
