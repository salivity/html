How CSP Nonce Whitelists Inline Scripts in HTML

This article explains how the Content Security Policy (CSP) nonce attribute allows developers to securely whitelist inline scripts in modern web applications. You will learn what a nonce is, how the server and browser collaborate to validate it, and how this mechanism prevents Cross-Site Scripting (XSS) attacks while still allowing critical inline JavaScript to execute.

A Content Security Policy (CSP) restricts the resources a browser is allowed to load and execute for a given page. By default, a strict CSP blocks all inline <script> elements because it cannot inherently distinguish between legitimate application scripts written by the developer and malicious scripts injected through an XSS vulnerability.

To resolve this issue without resorting to the dangerous 'unsafe-inline' directive, CSP introduces the nonce—an abbreviation for "number used once." A nonce is a cryptographically strong, pseudo-random token generated dynamically by the server for every individual HTTP request.

The whitelisting process functions through a three-step validation cycle between the web server and the client browser:

  1. Header Declaration: For every page request, the server generates a unique, unguessable string (typically Base64-encoded). The server includes this token in the Content-Security-Policy HTTP response header within the script-src directive, formatted as 'nonce-<token>':

    Content-Security-Policy: script-src 'nonce-rAnd0m12345' 'strict-dynamic';

  2. Attribute Injection: When rendering the HTML response, the server attaches the exact same token to the nonce attribute of every authorized inline script:

    <script nonce="rAnd0m12345">
  console.log("This authorized inline script will execute.");
</script>

  3. Browser Verification: When the browser parses the HTML document, it inspects every <script> element. It extracts the value of the nonce attribute and compares it directly against the nonce defined in the CSP header. If the values match identically, the browser executes the script. If the attribute is missing, malformed, or contains an incorrect value, the browser suppresses execution and logs a CSP violation.

This mechanism protects against injection attacks because an attacker cannot predict the unique nonce assigned to a victim's session. Any payload injected via input fields, query parameters, or stored databases will lack the correct nonce value for that specific request lifecycle, causing the browser to safely neutralize the malicious code. For maximum security, nonces must never be hardcoded, must be discarded after a single response, and should contain sufficient cryptographic entropy (at least 128 bits).
