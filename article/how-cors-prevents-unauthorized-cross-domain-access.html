How CORS Prevents Unauthorized Cross-Domain Access

Cross-Origin Resource Sharing (CORS) is a browser-enforced security mechanism that allows servers to control which external domains can access their resources. By working alongside the foundational Same-Origin Policy (SOP), CORS provides a framework of HTTP headers that dictate whether web applications running at one origin can read data requested from a different origin. This article explains how CORS functions, the critical role browsers play in enforcement, and how explicit server policies prevent malicious scripts from extracting sensitive data across domains.

The Foundation: The Same-Origin Policy

To understand CORS, one must first understand the Same-Origin Policy (SOP). Under the SOP, a web browser restricts scripts running on one origin from interacting with resources on another origin. An origin is defined by the combination of the protocol (e.g., HTTPS), host (e.g., example.com), and port (e.g., 443).

Without these restrictions, a malicious website loaded in a user's browser could execute JavaScript to send requests to the user's online bank, healthcare portal, or internal intranet. Since the browser automatically includes authenticated session cookies with requests to those domains, the malicious script could read the response and exfiltrate private data. The SOP prevents this scenario by disallowing the malicious site's scripts from reading cross-origin responses.

How CORS Safely Relaxes the Rules

While the SOP is essential, modern web architectures often require legitimate cross-origin communication, such as a frontend application hosted on frontend.example.com requesting data from an API on api.example.com. CORS provides a secure way to relax the SOP when explicitly intended by the resource owner.

CORS does not disable security; instead, it establishes an opt-in model managed via HTTP response headers:

  • Access-Control-Allow-Origin: Specifies which external origins are allowed to access the resource. If the value does not match the requesting site's origin (or is not a wildcard *), the browser blocks the requesting script from accessing the data.
  • Access-Control-Allow-Methods: Lists the HTTP methods (e.g., GET, POST, PUT, DELETE) permitted during a cross-origin request.
  • Access-Control-Allow-Headers: Dictates which custom headers can be sent with the actual request.
  • Access-Control-Allow-Credentials: Indicates whether the browser can expose the response to the frontend script when the request includes ambient credentials like cookies or HTTP authentication headers.

Preflight Requests for Unsafe Operations

For simple requests (typically basic GET or POST requests with standard headers), the browser sends the request immediately and checks the returning Access-Control-Allow-Origin header before letting JavaScript read the response.

However, for requests that might modify server state or use custom headers (such as PUT, DELETE, or requests carrying Authorization tokens), the browser initiates a "preflight" request. The browser automatically sends an OPTIONS request to the target server before dispatching the actual request. The server must reply with appropriate CORS headers confirming that the origin, method, and headers are authorized. If the preflight fails or returns unauthorized status, the browser drops the operation entirely, preventing the actual request from ever reaching the server.

Protecting Authenticated Data

The primary way CORS protects sensitive data is by strictly regulating credentialed requests. When malicious sites attempt to steal data, they rely on the victim's authenticated browser session.

Under CORS rules:

  1. A server must explicitly return Access-Control-Allow-Credentials: true to allow cross-origin reads on credentialed requests.
  2. When credentials are included, the server cannot use a wildcard (*) for the Access-Control-Allow-Origin header. It must explicitly state the exact matching origin of the client.

If a malicious site on attacker.com tries to fetch data from api.bank.com, the browser will attach the user's bank cookies, but api.bank.com will not list attacker.com in its Access-Control-Allow-Origin header. Consequently, the browser completely blocks the script on attacker.com from reading the returned HTML, JSON, or any other response data.

Summary of Browser Enforcement

It is crucial to note that CORS is a client-side, browser-enforced security control. It protects users from having their sensitive data read by untrusted third-party scripts. By requiring explicit, server-defined allowances through HTTP headers, CORS ensures that HTML documents and APIs remain strictly inaccessible to unauthorized domains.
