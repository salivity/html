Subresource Integrity: Securing HTML Script Tags

Subresource Integrity (SRI) is a web security standard that enables browsers to verify that external files—such as JavaScript scripts and CSS stylesheets—have not been maliciously altered or tampered with before execution. By using cryptographic hashes within the integrity attribute, website owners can ensure that third-party hosts like Content Delivery Networks (CDNs) deliver the exact, untampered code expected, effectively mitigating risks from CDN compromises and supply chain attacks.

What Is Subresource Integrity (SRI)?

Modern websites frequently rely on third-party CDNs to host shared libraries such as React, jQuery, or Bootstrap. While this improves delivery speed and caching efficiency, it introduces a significant security risk. If an attacker breaches the CDN or compromises the network pathway via a man-in-the-middle (MITM) attack, they can inject malicious code into the hosted file. Because the browser trusts the script source designated in the HTML, it executes the compromised code within the user's security context.

Subresource Integrity resolves this issue by providing a mechanism to validate the fetched asset against a predetermined cryptographic digest. If the file's content changes by even a single byte, the browser refuses to execute the script.

How the integrity Attribute Works

The integrity attribute is added directly to HTML <script> or <link> elements. Its value consists of at least one cryptographic hash algorithm prefix (such as sha256-, sha384-, or sha512-), followed by the base64-encoded hash value of the expected file content.

<script 
  src="https://cdn.example.com/npm/library@1.0.0/dist/library.min.js" 
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC" 
  crossorigin="anonymous">
</script>

When a browser encounters a script tag containing an integrity attribute, it executes the following verification process:

  1. Download: The browser fetches the resource from the specified URL.
  2. Hash Computation: Before executing or parsing the code, the browser hashes the downloaded file using the algorithm specified in the integrity attribute.
  3. Comparison: The calculated hash is compared against the string specified in the attribute.
  4. Execution or Rejection:
    • If the hashes match, the resource is deemed authentic, and the browser executes the script.
    • If the hashes do not match, the browser blocks the script from executing, discards the network response, and outputs a signature verification error to the developer console.

The Requirement for CORS

For cross-origin resources, SRI requires Cross-Origin Resource Sharing (CORS) to be enabled. Without CORS, the browser cannot read the raw response data to compute the hash due to the Same-Origin Policy.

To satisfy this requirement, the crossorigin="anonymous" attribute must be present on the <script> tag, and the serving server must respond with the Access-Control-Allow-Origin header set to allow the requesting origin (or set to *).

Generating SRI Hashes

Hashes can be generated via the command line using tools like OpenSSL:

cat library.min.js | openssl dgst -sha384 -binary | openssl base64 -A

Modern build systems and bundlers (such as Webpack, Vite, and Rollup) also offer plugins that automatically calculate and inject SRI hashes into generated HTML files during production builds.
