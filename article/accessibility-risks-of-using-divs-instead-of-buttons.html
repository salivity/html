Accessibility Risks of Using Divs Instead of Buttons

Replacing native HTML <button> elements with clickable <div> tags introduces severe accessibility barriers for users who rely on assistive technologies and keyboard navigation. While CSS can make a <div> look identical to a button and JavaScript can attach click behaviors, a <div> fundamentally lacks the built-in semantics, keyboard functionality, and state management that browsers provide by default. This article breaks down the primary hazards of creating fake buttons and why standard semantic elements are essential.

1. Loss of Keyboard Focusability

Native <button> elements automatically enter the natural tab order of a web page, allowing keyboard-only users to navigate to them seamlessly using the Tab key.

A standard <div> is a non-interactive grouping element and cannot receive focus by default. When developers attach a click listener to a <div>, keyboard users cannot tab to it or interact with it at all unless the developer explicitly remembers to add a tabindex="0" attribute.

2. Missing Keyboard Activation (Enter and Space)

Native buttons trigger their onclick event when a focused user presses either the Enter key or the Space key. Browsers also handle nuances automatically, such as scrolling prevention when pressing the Space bar on a button.

In contrast, an onclick listener bound to a <div> will only respond to mouse clicks by default. If a developer provides keyboard focus via tabindex="0", they must also manually write custom keydown or keyup event handlers to listen for both the Enter and Space keys. Without this redundant code, keyboard users can land on the element but remain completely unable to trigger the action.

3. Absence of Semantic Roles for Screen Readers

Screen readers rely on underlying HTML semantics to convey what an element is and what actions a user can perform on it. When a screen reader encounters a <button>, it announces the element’s label alongside its role, such as "Submit, button."

A <div> has no semantic role. A screen reader will typically interpret a clickable <div> as static text or a generic container. Blind and low-vision users will not be informed that the item is interactive, leading to confusion, missed interactions, or an inability to complete crucial tasks on the page.

4. No Native Disabled State

Native buttons support the disabled attribute. When disabled, the browser automatically prevents focus, blocks click and key events, and informs assistive technologies that the control is currently unavailable.

A <div> has no native concept of being disabled. Applying a .disabled CSS class only changes visual styling; assistive technologies and keyboard focus will continue to treat the element as normal. Properly disabling a custom <div> requires removing it from the tab order (tabindex="-1"), updating ARIA attributes (aria-disabled="true"), and manually intercepting JavaScript execution.

5. Incompatibility with Form Submissions

Inside an HTML <form>, a native button with type="submit" automatically submits form data and responds to the Enter key when pressed inside standard input fields. A clickable <div> has no relationship to forms and cannot trigger native submission, validation, or reset behaviors without extensive custom JavaScript scripting.

6. The Redundancy of Recreating the Wheel

To make a <div> as accessible as a native <button>, a developer must implement all of the following:

  • tabindex="0" to make it focusable.
  • role="button" so screen readers announce it properly.
  • A keydown listener listening for Enter and Space key codes.
  • e.preventDefault() logic to stop the page from scrolling on Space.
  • Dynamic aria-disabled and focus-management logic for inactive states.

Using a native <button> provides all of these critical features automatically, with zero performance overhead and no risk of implementation errors. Replacing it with a <div> creates unnecessary technical debt and degrades the user experience for people with disabilities.
