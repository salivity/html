How the HTML Tokenizer Converts Characters to Tokens

This article explains how an HTML parser breaks down raw input character streams into discrete tokens through the process of tokenization. By utilizing a state machine defined by the HTML5 specification, the tokenizer systematically reads characters one by one, tracks transitions across various internal states, decodes entities, and emits structured tokens such as tags, attributes, and text nodes to the subsequent tree-construction stage.

The State Machine Model

At the core of the HTML tokenizer is a finite-state machine (FSM). The tokenizer accepts a stream of Unicode code points as input and processes them sequentially. Depending on the current state and the incoming character, the tokenizer performs three primary actions: it updates its internal state, consumes the character, and optionally emits a token or appends data to a pending token.

Types of Tokens

The output of the tokenizer consists of specific token objects passed directly to the tree construction phase:

  • DOCTYPE tokens: Represent document declarations.
  • Start tag tokens: Contain the element name, self-closing flag, and an associated list of attributes.
  • End tag tokens: Represent closing tags.
  • Comment tokens: Enclose developer notes and commented-out markup.
  • Character tokens: Represent plain text and whitespace.
  • End-of-file (EOF) tokens: Signal the termination of the input stream.

Core States and Transitions

The tokenizer begins in the Data state. The lifecycle of character parsing moves through a set of foundational states:

  1. Data State: The tokenizer consumes characters normally. If it encounters regular text, it emits a Character token. When it encounters the less-than character (<), it transitions to the Tag Open state without emitting a token.

  2. Tag Open State: Upon reading <:

    • An exclamation mark (!) transitions the machine to states handling DOCTYPEs, comments, or CDATA blocks.
    • A forward slash (/) transitions to the End Tag Open state.
    • An ASCII letter transitions to the Tag Name state and initializes a new start tag token.
    • Any other character triggers a parse error, emits the < as a character, and returns to the Data state.

  3. Tag Name State: The tokenizer collects characters to build the element name (such as div or p).

    • A whitespace character transitions to the Before Attribute Name state.
    • A greater-than character (>) finalizes and emits the tag token, returning the machine to the Data state.
    • A forward slash (/) transitions to the Self-Closing Start Tag state.

  4. Attribute Parsing States: When attributes exist, the machine cycles through states such as Attribute Name, Before Attribute Value, and Attribute Value (which has variants for double-quoted, single-quoted, and unquoted values). The tokenizer constructs key-value pairs and appends them to the current start tag token before returning to the Tag Name or closing state.

Character Reference Decoding

When processing text inside the Data state or inside attribute values, the tokenizer handles character references (HTML entities like &amp; or &#123;). When an ampersand (&) is consumed, the machine enters specialized character reference states. It consumes the following characters to resolve the entity against a standard lookup table, replaces the sequence with the resolved Unicode character, and returns to its prior parsing state.

The Feedback Loop with Tree Construction

Tokenization does not happen entirely in isolation. The HTML parser operates with a feedback loop where the tree constructor can alter the state of the tokenizer.

For instance, when the tree builder processes a start tag for a <script>, <style>, or <textarea> element, it instructs the tokenizer to switch into raw text states (such as RAWTEXT, RCDATA, or Script Data). In these states, the tokenizer treats markup characters like < and > as plain text rather than the beginning of new tags, until it encounters a matching end tag sequence (e.g., </script>). This bidirectional communication ensures that embedded languages and plain text blocks are parsed according to their specific syntactic rules.
